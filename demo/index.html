AI QA Platform — demo guide

Record a browser flow once, generate a test suite from it, replay it with Playwright, and judge every scenario against evidence collected from the live page. This page is the demo script: where to start, what each step gives you, and what goes wrong if you skip it.

The one idea

A scenario is not a pass just because no step threw an exception.

Most record-and-replay tools report success whenever the clicks completed. This one collects evidence from the page — messages that appeared, native dialogs, table rows, downloads, console errors, whether the submit button was even clickable — and matches it against what the scenario said should happen. If nothing proved the expectation, the answer is UNVERIFIED, not a pass.

The second idea follows from the first: never turn ignorance into a failure. A false FAIL is the most damaging output a QA tool can produce, because it blames a working application and costs you the trust of the developers. Several features on this page exist only to prevent that.

Starting point

Prerequisites

# from the repo root
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m playwright install chromium

Run the server

.\run_server.ps1            # frees port 8000 first, then starts uvicorn
# options: -Port 8080  -Reload  -Address 0.0.0.0

Then open http://127.0.0.1:8000. Use run_server.ps1 rather than calling uvicorn directly — a raw call fails with WinError 10048 if a previous server still holds the port.

An API key is optional and is only needed to generate a suite. Recording, running, verdicts, self-healing, coverage enumeration, the defect importer and every report work with no key at all. If you have no key, skip step 4 of the demo path and use step 3 instead — you still get a full suite.

Data lives on disk, not in a database

projects/<project>/flows/<flow>/
    flow.json  actions.json  test_cases.json     the recording + the suite
    report.json  run_history.json  reports/      results
    screenshots/  videos/  traces/  downloads/   evidence

Back up projects/ before a demo. It is not tracked by git and there is no export feature yet. The recordings are the expensive part — losing the folder means re-recording every module by hand.

The demo path

Follow these in order. Each step names what you get, and what happens if you leave it out.

1

Record the module no API key

Launch the browser at the module's URL, log in, then reach the form: open the Add dialog, fill every field, save, and use the row action icons (view / edit / history / delete).

While you click, the recorder captures more than the clicks. It stores multiple candidate selectors per element, marks which fields the application says are mandatory, and watches for ~1.2 s after each click to record the effect — the URL change and the exact message text that appeared.

If you do Generation has real selectors and real message wording to work from, and knows which fields are mandatory.
If you don't reach the form There is nothing to generate from. The platform now refuses rather than inventing a suite — see Guards.
2

Keep login as its own flow no API key

Record the login once, in a flow named login, launched at the login page. Every other flow then reuses the stored session automatically.

If you do Business flows start already authenticated, and one credential change is one edit.
If you don't A flow named login but pointed at a business page is treated as an auth flow while its URL says otherwise — the exact mix-up that produced a suite of 17 fabricated scenarios.
3

Coverage → Enumerate field cases no API key

This is the step most people don't expect, and the best part of the demo. It reads the fields discovered on the real page and enumerates the test cases each one deserves from its own type and constraints — no model decides, so nothing can be quietly missed.

FieldCases producedIncludes
Required text11 empty, whitespace-only, 1 char, max length, max+1, leading/trailing spaces, special characters, unicode & emoji, SQL / HTML / template injection
Number7 zero, negative, decimal, non-numeric, maximum, above maximum, int32 overflow
Dropdown (2 options)3 no selection, plus each option

A 13-field form yields roughly 80–100 test cases for zero API calls. Passwords, OTP and captcha fields are never fuzzed — a locked account would fail every later scenario for reasons that have nothing to do with it.

If you do Field coverage is complete by construction and repeatable: the same form always yields the same set.
If you don't Coverage depends on the model remembering to write each permutation. It usually forgets several.
4

Generate the rest needs an API key

Two buttons, and both overwrite test_cases.json:

  • Multi-agent generate — Builder and Breaker in parallel, an Auditor reviewing, looping up to 3 rounds. Up to 9 API calls. The stronger suite generator.
  • QA specification — one call. Produces the suite plus the thinking: risks, requirement gaps, DB/API/security checklists, documentation, and a release-readiness call.

Order matters: run QA specification first, multi-agent second. The spec's extra artefacts survive, and multi-agent's better suite wins. Reverse it and you throw the better suite away.

If you do You get the scenarios that need genuinely different steps — create, edit, delete, search, export, audit history.
If you don't You still have step 3's enumerated cases. You lose the CRUD-lifecycle scenarios, which the Coverage report will list as gaps.
5

Add what a recording can't know mostly free

Three optional layers, all additive:

  • Rules — invariants in plain English ("Beam Length must reject 0 and negatives"). Enforced on every scenario and able to override a pass into a FAIL. 10 rule kinds. Translating English into a rule uses one API call; enforcing rules uses none.
  • Dependencies — declare what a flow provides and requires so a master is seeded once and its generated code flows into the next module as {{variable}}.
  • unique_by — the fields that together make a duplicate. Generates a two-phase duplicate test and its inverse: change only the last key field and the save must succeed.
If you do Duplicate tests actually create a duplicate, and cross-module data flows properly.
If you don't Duplicate tests pass without testing anything, and dependent dropdowns have nothing to select.
6

Pre-flight, then run no API key

Selector pre-flight loads the real page and checks every generated selector exists — cheap, and it catches a bad suite before a long run. Then run.

For a demo use headed mode so the audience watches the browser drive itself. For speed use headless with 5 workers; headed deliberately forces one scenario at a time.

If you do pre-flight Broken selectors surface in seconds instead of 20 minutes.
If you don't Every broken selector costs the full retry ladder before failing.
7

Read the results no API key

Results group under their parent scenario, so nine data rows against one field read as "7 of 9 test cases passed" — one finding, not nine defects. Failures also land in bugs.json, and exports cover HTML, CSV, JUnit XML and a Test Case Matrix with real Scenario | Test Case | Data columns.

How a verdict is decided

Four outcomes, and the third is the one that makes this tool trustworthy:

PASS Evidence confirmed what the scenario expected.
FAIL Evidence contradicted it.
UNVERIFIED Everything ran, nothing proved it. Deliberately not a pass.
CRASH The browser or page died.

Evidence the engine collects

On-screen messages, native dialogs, table rows, downloads, console and network errors, explicit VERIFY_* assertion outcomes (22 assertion verbs), captured variables, fields the engine auto-filled, whether the submit control was blocked, and whether a field refused the keystrokes.

Finding messages — four layers

  1. Seed selectors — the framework classes (PrimeNG, Material, Ant, Bootstrap, oxd).
  2. DOM diff — text that appeared after an action is a message, whatever its CSS. This finds a validation message in a class no framework list has ever heard of. On by default.
  3. Learning — a diff-discovered message's classes are remembered per project and read back on the next run, so the scanner sharpens as you use it.
  4. AI adjudication — optional, only for scenarios the rules can't settle.

Two things that look like a bug and are not. A form whose Save button stays disabled until valid is validating — the refusal is stronger evidence than a message, because the bad data never reached the server. And a numeric field that silently drops letters is validating at the input layer. Both are read as the application behaving correctly, where a naive engine reports "the invalid input appears to have been accepted".

What costs an API call, and what doesn't

Free No model involved

  • Recording, and effect capture
  • Enumerating field test cases
  • Page coverage — untested controls
  • Coverage report and gap checklist
  • Rule enforcement
  • Dependency seeding, unique_by
  • Defect-sheet import
  • Running, verdicts, self-healing
  • Every report and export

Costs calls Needs a key

  • Multi-agent generation — up to 9
  • QA specification — 1
  • Rule translation (English → rule) — 1
  • Selector repair — occasional
  • AI verdict adjudication — optional
  • Vision healing — off by default

Free-tier reality. Gemini's free tier is about 20 requests per day per model, so one multi-agent run can use half of it. The platform now refuses to start a run the day's allowance cannot finish, never retries a daily-quota error (retrying spent four requests to fail once), and says plainly when the cause is the quota rather than your key. /llm-status shows what is left.

Guards that refuse to lie

Each of these exists because the platform once produced a confident wrong answer.

GuardWhat it prevents
Grounding check Generating from a recording that never reached the page. A login-only recording aimed at a master-data URL is refused, with instructions — instead of 17 scenarios built entirely from words in a URL.
Grounding report Silence about guesswork. After generation it reports what share of selectors appear nowhere in the recording; above 70% the suite is flagged.
Never FAIL on ignorance Blaming a working app. If the engine has never seen where this application renders messages, "nothing appeared" is UNVERIFIED, not FAIL. Opt-in, because it moves existing numbers.
Ownership guardrail Auto-filling the very field a scenario is testing.
Created-record identity Asserting on a record from the original recording that no longer exists. The run verifies the record this scenario created and says so.
Sensitive-field skip Fuzzing a password and locking the account, failing everything after it.
Soft delete Permanent loss — deletes move to .trash/.

Defect log — a separate, additional feature

Upload an existing defect sheet and re-test the bugs it records. Needs a Module column and an Expected Result column; also reads Defect ID, Steps to Reproduce, Actual Result, Priority and Status. CSV and .xlsx both work.

It is deliberately disconnected from the main flow. Defect scenarios never enter a module's test_cases.json. They get their own <Flow> [defects] flow with its own report, so running them — or not — has no effect on your real suites. A test asserts the module's own suite is byte-for-byte unchanged after an import.

Your Expected Result column does the heavy lifting: it is already the kind of checkable sentence the verdict engine reads. Steps to Reproduce is prose — field names are resolved against the labels already discovered for that module, and anything that can't be resolved is reported, not guessed. A relative value ("an Outer Diameter less than the Inner Diameter") comes back with a suggested value for you to accept, because a fabricated number would make a defect look tested when it wasn't.

Traps worth demoing

A recorded selector is one literal spelling of one control, and a real screen defeats it in predictable ways. The engine handles each of these so the same test case keeps working without anyone editing it — and tests/selftest_app/chain.html reproduces all of them, which makes them safe to show live.

What the screen doesHow the engine copes
A closed dialog sits before the open one in the DOM Matches are scanned for one actually on screen, instead of failing on the hidden first match.
Identical fields behind the dialog Every candidate is tried inside the open dialog before any is tried page-wide, so the dialog always wins.
The button says "Update", not "Save" Synonyms — Save↔Update↔Submit, No↔Cancel↔Close, Export↔Download, plus icon-only buttons. Reject synonyms never include confirm words.
Mandatory field the recording missed The form is completed automatically — except the field under test.
"No data available" vs "No records found" Recognised as the same empty state; a framework difference is not a defect.
Audit history with blank Date/User Caught as a real finding, even though every row is present and every step "succeeds".

Best 60 seconds of any demo: open the Audit History of a master record. Every row is there, every step passes, and a conventional suite calls it green — while the DATE/TIME and USER columns are empty and some rows record a change from 2344.0000 to 2344, which is no change at all. This platform reports both.

Flags & reference

Environment flags

VariableDefaultWhat it does
GEMINI_API_KEY— Only generation needs it.
GEMINI_MODELgemini-3.6-flash Switching model is a valid fix for a small quota.
QA_VISION_HEALING0 Screenshot-to-model healing. Off because it costs 15–20 s per failed step and spends generation quota during test runs.
QA_DOM_DIFF_MESSAGES1 Message layer 2. Only ever adds messages the static list can't see.
QA_STRICT_MESSAGE_CONFIDENCE0 Never FAIL on ignorance. Off because it moves existing verdict numbers.
QA_LLM_DAILY_BUDGET20 Assumed daily allowance, used to warn. Set 0 once billing is on.
QA_MAX_WORKERS5 Parallel scenarios. Headed mode always uses 1.
QA_WORKSPACErepo root Where projects/ and logs/ live.
QA_API_KEYempty Protects the platform's own HTTP API. Empty disables auth.

A trap worth knowing: .env beats a flag you unset in the shell. The config loader fills in anything absent from the environment, so deleting a variable lets .env put it straight back. Edit .env itself.

Verifying the platform

.venv\Scripts\python.exe -m pytest tests -q                  # 117 unit tests
.venv\Scripts\python.exe tests\e2e_selftest.py               # real browser, 13 verdict cases
.venv\Scripts\python.exe tests\e2e_chain.py                  # dependency chain, rules, traps
.venv\Scripts\python.exe tests\smoke_ui.py                   # boots the server, drives the UI
.venv\Scripts\python.exe tests\integration_api.py            # 51 API checks
.venv\Scripts\python.exe tests\regression_existing_data.py   # backward compatibility

All six run offline with no API key and are safe to run in front of an audience. The browser suites drive a bundled sample app, so they touch no real system.
